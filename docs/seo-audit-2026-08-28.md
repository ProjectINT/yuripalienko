## 2. P0 — Превью в соцсетях и мессенджерах

### P0-1. Три страницы без `og:image` — 6 URL из 18

Проверено на проде:

| URL | `og:image` |
|---|---|
| `/en`, `/ru` | ✅ |
| `/en/works`, `/ru/works` | ✅ |
| `/en/pricing`, `/ru/pricing` | ✅ |
| `/en/cv`, `/ru/cv` | ✅ |
| `/en/palistor`, `/ru/palistor` | ✅ |
| `/en/articles/<slug>`, `/ru/...` | ✅ |
| **`/en/about`, `/ru/about`** | ❌ |
| **`/en/contacts`, `/ru/contacts`** | ❌ |
| **`/en/articles`, `/ru/articles`** | ❌ |

**Причина.** `opengraph-image` — конвенция **сегмента маршрута**, а не наследуемые метаданные. Документация Next 16 (`node_modules/next/dist/docs/.../opengraph-image.md`, строка 6): *«позволяют задать Open Graph и Twitter изображения для сегмента маршрута»*. Картинка из `app/[lang]/opengraph-image.tsx` покрывает только `/[lang]`, вниз по дереву не идёт. Там, где файл создан (`works`, `pricing`, `cv`, `palistor`, `articles/[slug]`), картинка есть; где не создан — нет.

**Последствие хуже, чем «нет картинки».** `metaFor` всё равно ставит `twitter:card = summary_large_image`. Карточка без изображения при этом типе схлопывается в текстовую полосу или отбрасывается — в X, Telegram, Slack и LinkedIn ссылка на `/contacts` и `/about` выглядит голой. Это именно те две страницы, которые чаще всего кидают в личку.

**Фикс — 3 файла по 12 строк**, ровно по образцу `works/opengraph-image.tsx`:

```
app/[lang]/about/opengraph-image.tsx      → ogImage(about.title, about.lead)
app/[lang]/contacts/opengraph-image.tsx   → ogImage(contacts.title, contacts.intro)
app/[lang]/articles/opengraph-image.tsx   → ogImage(articles.title, articles.intro)
```

Оценка: **30 минут.** Это единственный пункт всего аудита, который надо сделать сегодня.

### P0-2. `og:image:alt` не переведён на русском

| URL | `og:image:alt` |
|---|---|

| `/ru/works` | `Palisoft portfolio — SaaS, marketplaces and BI systems` |

`export const alt` — статическая строка, одна на обе локали. Решение уже найдено и применено на `/palistor`: `generateImageMetadata` получает `params` и отдаёт локализованный alt. В коде это отмечено как «отдельная задача» — вот она.

Перевести четыре страницы на `generateImageMetadata`, поля `ogAlt` завести в `content/{ru,en}/*.json` (как в `palistor.json`). Побочный эффект — URL картинки получит суффикс `/og`, как у `/palistor`; на индексацию не влияет, но старые расшаренные ссылки перекэшируются.

Оценка: **1 час.**

### P0-3. Любая битая ссылка превьюшится как главная

`/en/nope-xyz` отдаёт 404 по статусу, но в `<head>`:

```html
<meta name="robots" content="noindex"/>                      ← из not-found.tsx
<meta name="robots" content="noindex, nofollow, nocache"/>   ← из [...rest]
<link rel="canonical" href="https://palisoft.ru/en"/>        ← протёк из layout
<link rel="alternate" hrefLang="ru" href="https://palisoft.ru/ru"/>
<meta property="og:title" content="Palisoft — SaaS, Marketplace & MVP Development Studio"/>
<meta property="og:image" content="https://palisoft.ru/en/opengraph-image?..."/>
```

`generateMetadata` в `app/[lang]/[...rest]/page.tsx` возвращает только `robots`, поэтому `title`, `canonical`, `alternates` и весь OG-блок наследуются от layout — то есть от главной. Два конфликтующих тега `robots` в одном документе — отдельная неряшливость.

Практический эффект: опечатка в ссылке, старый URL из переписки, битая ссылка из чужой статьи — всё это разворачивается в мессенджере как полноценная карточка главной страницы, и человек не понимает, что попал на 404. Для поиска ущерба нет (статус 404 перевешивает), для входящих обращений — есть.

**Почему так вышло.** `/en/nope-xyz` матчится на `[...rest]`, тот бросает `notFound()`, и метаданные разрешаются по ближайшему сегменту — `[lang]`. А у `[lang]` есть и свой `opengraph-image.tsx`, и `metaFor(lang, '', …)` из layout. Отсюда и канон главной, и её карточка.

**Фикс** — задать в `[...rest]` собственные значения вместо наследуемых:

```ts
// app/[lang]/[...rest]/page.tsx
export function generateMetadata(): Metadata {
  return {
    title: '404',
    robots: { index: false, follow: false },
    alternates: { canonical: null, languages: {} },
    openGraph: null,
    twitter: null,
  }
}
```

`null` как способ погасить унаследованное поле в документации Next 16 явно не описан — резолвер его так трактует, но проверить надо в собранном HTML, а не на слово. Если не сработает, запасной вариант — не наследовать вовсе: убрать OG-блок из layout в отдельный `metaFor` главной страницы (`app/[lang]/page.tsx` сейчас своего `generateMetadata` не имеет вообще и живёт на метаданных layout — это же и есть корень протечки).

Оценка: **20 минут** + проверка вывода.

### P0-4. Нет `twitter:site` / `twitter:creator`

`metaFor` ставит только `card`, `title`, `description`. В X карточка выйдет без привязки к аккаунту — ни ссылки на профиль, ни атрибуции автора. Если аккаунта в X нет, пункт закрывается решением «не заводим» (тогда честнее ставить `card: summary` там, где картинки нет), а не молчанием.

Оценка: **10 минут** после того, как появится хэндл.

## 3. P1 — Технические пробелы

### P1-1. Сайта нет в индексе, и попросить обход некому

`site:palisoft.ru` не возвращает ни одной страницы домена. При открытом `robots.txt`, живом sitemap и нулевых внешних ссылках это ожидаемо: краулеру неоткуда узнать о домене.

В `app/[lang]/layout.tsx:46` блок верификации лежит закомментированным — Search Console, Bing и Яндекс.Вебмастер не подключены.

**Это самый дорогой по эффекту пункт всего документа.** Пока нет Search Console, у вас нет ни отправки sitemap, ни запроса на индексацию, ни данных о запросах, ни отчёта о покрытии — то есть весь выполненный технический этап не конвертируется ни во что.

Порядок: раскомментировать `verification`, подтвердить домен в трёх панелях, отправить sitemap, запросить индексацию главной. Данные начнут копиться с даты подключения — каждая неделя промедления теряется навсегда.

Оценка: **1.5 часа**, включая ожидание подтверждения DNS.

### P1-2. `lastmod` в sitemap врёт на 16 URL из 18

`app/sitemap.ts:20` — `const BUILD_TIME = new Date()`, и он подставляется всем статическим маршрутам. Любой деплой (правка стиля, фикс опечатки в футере) объявляет поисковику, что обновились все 16 страниц одновременно. Google быстро перестаёт доверять такому `lastmod` и начинает игнорировать его целиком — включая честные даты статей, которые сейчас проставлены правильно.

**Фикс:** держать дату правки контента рядом с контентом — поле `updated` в `content/{lang}/*.json`, как это уже сделано для постов. Пока полей нет — лучше не отдавать `lastModified` для статических маршрутов совсем, чем отдавать время сборки.

Оценка: **1.5 часа.**

### P1-3. Статья без картинки в разметке и без авторских мета-тегов

На `/en/articles/rynok-po-i-investicii-v-ai-2022-2026` из `article:*` присутствует только `published_time`. Нет:

- `article:author`, `article:tag`, `article:section`;
- `<meta name="author">` (в Next — поле `authors` в метаданных);
- `image` в `BlogPosting` — потому что у поста `cover: null`, а `lib/schema.ts:119` ставит `image` только при своей обложке.

`image` — обязательное поле для Article rich results в Google. Без него разметка валидна, но карточку в выдаче не даст.

Комментарий в коде объясняет, почему динамический OG-URL не годится для `image`, и это верно. Решение — не переиспользовать OG-роут, а завести посту настоящую обложку в `public/posts/` и заполнить `cover`.

Оценка: **1 час** + отрисовка обложки.

### P1-4. Английская статья живёт по русскому транслитерированному слагу

`/en/articles/rynok-po-i-investicii-v-ai-2022-2026` — при английском заголовке *«The software market 2022–2026 and the shift of investment into AI»*. Слаг участвует в релевантности и в том, как ссылку читает человек; латинская транслитерация русской фразы в англоязычном URL не работает ни там, ни там.

Схема «один слаг на пару» заложена в `lib/posts.ts` и `dynamicParams = false` намеренно — менять её ради одного поста дорого. Но пока пост ровно один, цена перехода на пару слагов (`slug` в JSON каждой локали) минимальна, а с каждой следующей статьёй растёт.

**Решать сейчас, пока статья одна.** Оценка: **2–3 часа.**

### P1-5. Нет RSS/Atom

`/feed.xml` и `/rss.xml` → 404. Для инженерного блога это канал дистрибуции (агрегаторы, читалки, автопостинг) и один из немногих способов получить первые внешние ссылки без ручного аутрича.

Оценка: **1 час** — маршрут `app/feed.xml/route.ts` поверх готового `getPosts()`.

### P1-6. `www.palisoft.ru` отдаёт самоподписанный сертификат

`curl https://www.palisoft.ru/` → `SSL certificate problem: self-signed certificate`. Внешних ссылок на www сейчас нет, поэтому дублей в индексе не возникнет, но любой, кто наберёт адрес с www вручную, получит страницу с предупреждением браузера о небезопасном соединении.

**Фикс:** либо выпустить сертификат на www и повесить 301 на апекс, либо снять A/CNAME-запись www совсем — тогда домен просто не резолвится, и это честнее битого TLS.

Оценка: **30 минут** на стороне Dockhost/DNS.

### P1-7. `sameAs` без LinkedIn

`lib/schema.ts:13` — GitHub, Telegram, dev.to, vc.ru. Для Knowledge Panel и для сущности `Person` LinkedIn — самый весомый из профилей, и его нет. Вопрос Q6 из прошлого плана так и остался открытым.

Связка должна быть двусторонней: профили обязаны ссылаться на `palisoft.ru`, иначе `sameAs` — односторонняя декларация без подтверждения.

Оценка: **20 минут** после того, как придут URL.

### P2-2. H1 на всех страницах — пункты меню

`Work`, `About`, `CV`, `Contact`, `Writing`, `Pricing`. Один H1 на страницу — формально верно, Lighthouse SEO 100. Но H1 — сильнейший внутристраничный сигнал темы, и сейчас он несёт ровно ноль информации о том, чем страница отличается от миллиона других страниц со словом «Work».

`seoTitle` при этом написаны хорошо (`Portfolio: SaaS, Marketplaces & BI Systems | Palisoft`). Разрыв между title и H1 — чистая потеря: смысл уже сформулирован, просто не доехал до заголовка.

**Фикс:** развести навигационную подпись и H1 — в `content/{lang}/*.json` уже есть `title`, добавить `h1` рядом. Меню продолжает показывать `Work`, страница показывает `SaaS-платформы, маркетплейсы и BI-системы: кейсы`.

Оценка: **2 часа** на обе локали.

### P2-3. 11 кейсов без собственных URL

`content/en/works.json` — 11 проектов, у каждого `role`, `period`, `company`, `summary`, 3–6 `highlights`, 8–13 позиций стека. Всё это ужато в 500 слов одной страницы. Разложенное по `/works/[slug]` это 11 страниц по 300–500 слов с уникальными длиннохвостыми запросами — единственный на сайте контент, который уже написан и просто не разложен.

Скриншоты есть у 7 из 11: без картинок остались `bi-platform`, `paliproxy`, `elit-taxi`, `freelance`. У четырёх нет и внешней ссылки — им нужна отдельная страница тем более, иначе подтверждения существования у них нет вовсе.

Пункт был в прошлом плане как P1-3 и остался невыполненным. **Это лучшее соотношение эффекта к затратам на сайте.**

Оценка: **6–8 часов** (маршрут + `generateStaticParams` + OG + `CreativeWork`-разметка + крошки + перелинковка).

### P2-4. Пятнадцать скриншотов существуют только внутри WebGL

На главной **ноль тегов `<img>`**. Трейс показывает, что 17 файлов `/works/cards/*.webp` грузятся — но как текстуры three.js, внутрь `<canvas>`, помеченного `aria-hidden`. Для Google Картинок, для соцсетей и для краулера без WebGL их не существует.

Это не баг — сцена задумана декоративной. Но полноразмерные версии тех же скриншотов лежат в `/works/*.webp` и на `/works` отдаются через `next/image` корректно. Пункт закрывается сам собой вместе с P2-3: страницы кейсов дадут этим картинкам настоящие `<img>` с alt и подписью.

| `en/cv.json` | `seoDescription` | **159** | ≤155 |

Особенно обидно на `/pricing`: `... — от 500 000 ₽ | Palisoft` — цена, главный крючок сниппета, стоит ровно в зоне обрезки.

Прямых потерь в ранжировании нет, но обрезанный сниппет хуже кликается. Полезно добавить в CI простую проверку длин по `content/**/*.json` — иначе поля разъедутся снова через три правки.

Оценка: **1 час** на переписывание + **1 час** на проверку в CI.

### P2-6. `FAQPage` только на `/palistor`

Функция `faqPage` написана и используется один раз. На `/pricing` — 171 слово и ни одного ответа на очевидные вопросы: что входит в оценку, сроки, порядок оплаты, кому принадлежит код, что после запуска.

FAQ-сниппеты Google с 2023 года показывает почти только гос- и медресурсам, так что визуального выигрыша в выдаче ждать не стоит. Но `robots.txt` осознанно пускает GPTBot, ClaudeBot и Perplexity, а вопрос-ответный формат — лучший для извлечения фактов LLM. Плюс объём страницы вырастет вдвое, и закроются возражения до созвона.

Это ровно вопрос Q10 из прошлого плана, оставшийся без ответа. Оценка: **2–3 часа**, в основном на текст.

### P2-7. Раздел «Статьи» — одна публикация

`/articles` = 1 свой пост + список внешних ссылок. Инфраструктура блога (JSON-блоки, подсветка кода, OG, `BlogPosting`, время чтения) построена под поток и стоит без нагрузки.

Органика инженерного сайта живёт на статьях. Один пост — это не блог, это доказательство, что блог технически работает. Пока нет ответа на Q7 прошлого плана («готовы писать раз в две недели?»), раздел будет висеть мёртвым весом. Ответ здесь важнее любой строчки кода в этом документе.

## 5. P3 — Производительность (замерено, проблем нет)

Lighthouse mobile, navigation, `https://palisoft.ru/en`:

| Категория | Балл |
|---|---:|
| SEO | **100** |
| Accessibility | **100** |
| Agentic Browsing | **100** |
| Best Practices | 77 |

Performance-трейс:

- **LCP 237 мс** (TTFB 169 мс + render delay 68 мс) — рендер-блокирующих запросов, влияющих на LCP, нет
- **CLS 0.00**
- HTML 50 КБ → **8.8 КБ** по проводу, `x-nextjs-cache: HIT`
- **CrUX: данных нет** — полевых метрик у Google по этому домену не накоплено, трафика слишком мало

Best Practices 77 — сторонние cookie Яндекс.Метрики. Метрика грузится только после согласия (`ConsentGate` → `strategy="lazyOnload"`), в LCP и TBT не участвует. Балл поднять нельзя, не убрав Метрику; трогать не нужно.

**Что всё же стоит знать.** Главная догружает после `window.load` два тяжёлых объекта:

| Ресурс | Размер по проводу |
|---|---:|
| чанк three.js / R3F (`2vuze8p3iy6wb.js`) | **272 КБ** (brotli) |
| `/hdri/studio.hdr` | **411 КБ** (без сжатия) |

Итого ~**680 КБ** сверх страницы. На LCP это не влияет — `ssr: false`, загрузка после первой отрисовки, режимы `lite`/`static` для тач и `prefers-reduced-motion` разведены аккуратно. Но на мобильном трафике это ощутимо, а разбор HDR грузит главный поток и рискует INP.

Дешёвые улучшения, если решите заняться: отдавать `.hdr` со сжатием (текстовый формат, gzip даст 2–3×) или заменить на предзапечённый `.env`/сгенерированное окружение меньшего размера; в режиме `lite` HDRI можно не грузить вовсе.

**Отдельно:** трейс показал, что за одну загрузку главной `/en/contacts` префетчится **6 раз** с разными `_rsc`-хэшами, `/en/works` — 3 раза, `/en/palistor` — 4. Это поведение сегментного префетча Next 16 в связке с двумя навигациями (`SideNav` + `MobileNav`), рендерящими один и тот же список ссылок. На SEO не влияет, на трафик и на нагрузку — да. Стоит посмотреть, не рендерятся ли обе навигации одновременно вместо переключения по медиазапросу.

# превью: из 16 маршрутов ниже картинка есть у 10, должно быть у 16

         /ru /ru/about /ru/contacts /ru/articles /ru/works /ru/cv /ru/pricing /ru/palistor; do

done

# картинка реально рендерится, а не 500
curl -sI "https://palisoft.ru/en/about/opengraph-image" | head -3

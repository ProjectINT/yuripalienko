## 1. Развилка 1 (главная): когда именно «автоматом» — **решено: A**

Слово «автоматом» имеет два разных смысла, и от выбора зависит примерно всё остальное.

### Вариант A — на сборке (SSG). **Выбран владельцем**

Кладём `.md` в репозиторий → `git push` → Dockhost сам пересобирает образ → статья в проде через ~3–5 минут. «Автоматом» здесь означает: **ноль правок кода и JSON**, файл — единственное действие.

- Плюсы: статический HTML (лучший TTFB и индексация); все зависимости парсинга — `devDependencies`, как shiki, и **не едут в рантайм-образ**; контент лежит в git (история, откат, ревью, бэкап бесплатно); ничего не меняется в архитектуре — тот же образ-неизменяемый-артефакт.
- Минусы: пересборка на каждую статью (~3–5 мин, руками ничего делать не надо); опечатку в тексте нельзя починить без пуша.

### Вариант B — в рантайме, из примонтированного тома

Кладём `.md` в volume на сервере → статья появляется без пересборки (сразу или по окну ISR).

Что для этого нужно на самом деле:
- том в панели Dockhost (в `docs/deploy-dockhost.md` тома не описаны — **надо проверить, что платформа их даёт**);
- `dynamicParams = true` + `revalidate` или полностью динамический рендер вместо SSG;
- remark/shiki переезжают в `dependencies` → образ растёт (сейчас ~228 МБ);
- контент вне git: бэкап, история и ревью — вручную;
- статья, положенная в том, не попадает в `generateStaticParams` на сборке → её URL рендерится по первому запросу (ISR) или каждый раз (dynamic).

Смысл имеет ровно один сценарий: публиковать хочется с телефона/по SFTP, без git. Для персонального блога с несколькими статьями в месяц это дорогая покупка.

### Вариант C — гибрид

SSG для файлов из репозитория + ISR-окно для тома. Складываются оба набора минусов, выигрыш — только если реально нужны оба способа публикации. Не рекомендуется.

> **Решение владельца: A.** Он единственный, который ничего не ломает в существующей архитектуре, и при этом «положил файл — статья появилась» выполняется буквально: push и есть публикация. Переход A → B позже стоит примерно один день и не требует переписывать парсинг (см. §3, движок один и тот же).

## 2. Развилка 2: где лежат файлы

| Место | Работает | Подводные камни |
|---|---|---|
| **`content/blog/{ru,en}/*.md`** ✅ | да | рядом с существующим `content/{ru,en}/*.json` — одна логика для всего контента; в git; наружу не отдаётся |
| `public/blog/*.md` | да | `public` отдаётся как есть → **сырой файл доступен по `https://palisoft.ru/blog/foo.md`**: дубль контента для поисковика, лечится `X-Robots-Tag: noindex` в `headers()` или rewrite'ом. Плюс: `public` целиком копируется в рантайм-образ (это удобно для §1-B) |

> **Рекомендация: `content/blog/{ru,en}/`.** Если позже захочется вариант 1-B, каталог просто монтируется томом по тому же пути — код чтения не меняется.

**Отдельная находка.** OG-картинки рендерятся **в рантайме** (см. §0), а `content/` в рантайм-образ сейчас не копируется. Значит для OG-картинки статьи нужно либо добавить в `Dockerfile` строку

```dockerfile
COPY --from=builder --chown=node:node /app/content ./content
```

(несколько десятков КБ текста — дёшево), либо пререндерить OG на сборке. Рекомендуется первое: одна строка, и заодно готовит почву под §1-B.

## 3. Развилка 3: чем парсить markdown

| | Вариант 1: `@next/mdx` | Вариант 2: unified/remark ✅ | Вариант 3: `markdown-it` |
|---|---|---|---|
| Пакеты | `@next/mdx`, `@mdx-js/loader`, `@mdx-js/react`, `@types/mdx` | `unified`, `remark-parse`, `remark-gfm`, `remark-rehype`, `rehype-slug`, `rehype-stringify`, `@shikijs/rehype`, `gray-matter` | `markdown-it` + 2–3 плагина + ручная интеграция shiki |

| Фронтматтер | не поддерживается из коробки, нужны плагины | `gray-matter` | `markdown-it-front-matter` |
| GFM-таблицы (есть в образце) | через `remark-gfm` | через `remark-gfm` | из коробки |
| Якоря у заголовков, TOC | плагины | `rehype-slug` + `rehype-autolink-headings` | `markdown-it-anchor` |
| Подсветка кода | плагин | `@shikijs/rehype` — **та же тема vesper, что на `/palistor`** | вручную |
| React-компоненты внутри статьи | ✅ главный плюс | ❌ (нужен свой синтаксис) | ❌ |
| Совместим с рантайм-режимом (§1-B) | ❌ контент компилируется в модуль на сборке | ✅ тот же код читает файл когда угодно | ✅ |
| Число зависимостей | 4 (+ прод-рантайм) | ~8, все — `devDependencies` при варианте A | 3–4 |

> **Рекомендация: 2 (unified/remark).** Причины по важности: (а) обычный `.md` работает как есть — образец файла не потребует ни одной правки; (б) тот же код обслуживает и вариант 1-B, если он когда-нибудь понадобится; (в) shiki уже в проекте и подключается одним плагином, статьи получат подсветку, идентичную странице `/palistor`; (г) при варианте 1-A всё это остаётся `devDependencies` и в рантайм-образ не едет.

**Как отдаём в React.** Два шага:
1. Сейчас: пайплайн отдаёт строку HTML → `dangerouslySetInnerHTML` (ровно как уже сделано в [components/ui/CodeBlock.tsx](../components/ui/CodeBlock.tsx) для shiki). Безопасно: источник — свои файлы из репозитория, не пользовательский ввод.
2. Потом, если понадобится: `hast-util-to-jsx-runtime` вместо `rehype-stringify` — тогда `<a href="/...">` становится `next/link` (префетч), а `<img>` — `next/image`. Отдельная задача, не блокирует запуск.

**Если статьи когда-нибудь начнут приходить не от владельца** — добавить `rehype-sanitize`. Пока не нужен.

## 4. Развилка 4: фронтматтер или вывод из файла

Образец фронтматтера не имеет. Требовать его — значит нарушить «положил файл и всё».

**Рекомендуется гибрид: всё выводится из файла, фронтматтер только переопределяет.**

| Поле | Откуда по умолчанию | Переопределение |
|---|---|---|
| `slug` | имя файла без расширения (в образце уже слаг) | — |
| `title` | первый `# H1`, **и он вырезается из тела** — иначе заголовок задвоится с `PageHeader` | `title:` |
| `summary` | первый абзац, обрезанный до ~160 символов; он же `seoDescription` и подзаголовок OG | `summary:` |
| `date` | префикс имени файла `YYYY-MM-DD-slug.md`, иначе mtime файла | `date:` |
| `lang` | папка (`content/blog/ru/`) | `lang:` |
| `tags` | пусто | `tags: [a, b]` |
| `draft` | `false` | `draft: true` — файл не попадает ни в сборку, ни в sitemap |
| `cover` | нет | `cover: /blog/foo.webp` |

⚠️ **mtime внутри Docker-сборки ненадёжен**: в контексте сборки время файла — это время чекаута, а не дата написания статьи. Поэтому дата берётся из фронтматтера или из префикса имени файла; mtime — только последний фолбэк, и в проде он даст дату сборки. Практический вывод: **договориться называть файлы `2026-08-16-slug.md`** либо ставить одну строку `date:` во фронтматтере.

Для образца ничего добавлять не придётся вообще: title, summary и lang выведутся, дата — префиксом имени при копировании в `content/blog/ru/`.

## 5. Развилка 5: двуязычность — **решено: перевод обязателен**

Сквозное правило сайта (`docs/palistor-page-plan.md` §12): всё, что видит посетитель, существует в обеих локалях. **Владелец распространил его и на статьи: публикуется только то, что переведено.** Статья из образца — пока только на русском, значит перед публикацией её нужно перевести (шаг 11 в §10).

Схема хранения: `content/blog/ru/{slug}.md` и `content/blog/en/{slug}.md`, **одинаковый слаг = пара переводов**. Это то, что даёт корректный `hreflang` и позволяет `metaFor` выдавать честные alternates без единой строчки исключений.

Что происходит, если пара неполная (файл положили в одну папку и забыли про вторую):

| Поведение | Оценка |
|---|---|
| **Пропустить статью + громкое предупреждение в лог сборки** ✅ | статья не публикуется ни в одной локали, деплой при этом жив. Правило соблюдено, забытый перевод виден в логе пайплайна |
| Уронить `pnpm build` | правило соблюдается жёстче некуда, но одна забытая строка кладёт весь деплой, включая не связанные с блогом правки |
| Опубликовать в одной локали | прямо противоречит принятому решению |

> **Реализация:** `lib/posts.ts` собирает пары по слагу; непарные слаги отсеиваются и печатаются в консоль как `[blog] пропущено: {slug} — нет перевода {lang}`. `generateStaticParams` возвращает только полные пары, поэтому непарная статья физически не имеет URL ни на `/ru`, ни на `/en` (сработает `[...rest]` → 404).

Отдельно: `draft: true` во фронтматтере (§4) — легальный способ держать наполовину готовую пару в репозитории, не публикуя её.

## 6. Развилка 6: URL — **решено: `/articles/{slug}`**

| | Схема | Плюсы | Минусы |
|---|---|---|---|
| **1** ✅ | `/{lang}/articles/{slug}`, `/articles` остаётся индексом | пункт меню, sitemap-строка и seo-plan уже существуют; на индексе в одном месте и свои статьи, и внешние публикации | «articles» чуть длиннее «blog» |

> **Решение владельца: 1.** Индекс `/articles` перестраивается так: сверху — свои статьи (заголовок, дата, время чтения, теги), ниже, отдельным блоком, — существующий список внешних публикаций из `articles.json`. Голый `/articles/foo` без локали, как и остальные пути, уводится 307-редиректом в [proxy.ts](../proxy.ts) — менять там ничего не нужно.

7. `opengraph-image.tsx` для статьи + строка `COPY content` в `Dockerfile`.
8. `sitemap.ts`.
9. Расширить `lib/highlight.ts` + фолбэк на незнакомый язык.
10. Положить образец в `content/blog/ru/2026-08-16-rynok-po-i-investicii-v-ai-2022-2026.md`, собрать, посмотреть. На этом шаге статья ещё **не публикуется** — пары нет, сборка её пропустит и скажет об этом в логе. Это и есть проверка механизма из §5.
11. Английский перевод в `content/blog/en/` под тем же слагом → пара полная → статья выходит в обеих локалях. **Обязательный шаг, а не опция** (решение владельца, §5).

Шаги 1–5 дают работающий блог; 6–9 — то, ради чего на этом сайте вообще всё делается (SEO); 10–11 — контент.

## 11. Риски и грабли

- **Незнакомый язык в блоке кода роняет сборку.** Shiki на неизвестном `lang` бросает исключение. Нужен белый список + тихий фолбэк в простой `<pre>`. Иначе статья, написанная в отпуске, ломает прод-деплой.
- **Задвоенный H1.** Заголовок рисует `PageHeader`, а в теле остаётся исходный `# ...`. Вырезать первый H1 обязательно.
- **`.md` в `public/` отдаётся сырым.** Только для варианта §2-public: закрыть `X-Robots-Tag: noindex`.
- **mtime в Docker = время чекаута.** См. §4: дата — из имени файла или фронтматтера.
- **Русские названия месяцев.** `Intl.DateTimeFormat('ru')` на `node:24-alpine` — проверить в контейнере, а не только локально (пункт чек-листа).
- **Время сборки растёт линейно** по числу статей (shiki на каждую). До нескольких десятков статей незаметно; дальше — кеш пайплайна.
- **`INDEXING_ENABLED`.** Пока флаг выключен, `sitemap.ts` возвращает пустой массив, а `robotsMeta` ставит `noindex` — статьи не проиндексируются. Это существующее поведение, а не баг; помнить при проверке.
- **Битые внутренние ссылки в тексте.** Ссылка `/palistor` из markdown должна вести на `/{lang}/palistor`. Либо чинить шагом пайплайна, либо писать в статьях полные пути с локалью.

## 12. Чек-лист приёмки

- [ ] Пара файлов положена в `content/blog/{ru,en}/`, `pnpm build` — статья доступна в обеих локалях, код не тронут
- [ ] `/ru/articles` и `/en/articles` показывают её первой; блок внешних публикаций на месте
- [ ] Файл без пары: сборка не падает, статья не публикуется ни в одной локали, в логе есть предупреждение с именем слага
- [ ] `hreflang` в паре ссылаются друг на друга, canonical у каждой страницы — на себя
- [ ] Таблицы образца скроллятся на 320px, вёрстка страницы не разъезжается
- [ ] Заголовок не задвоен; дата — дата написания, не дата сборки
